- (direction) Eric demande une spec en français décrivant les règles métier implémentées par cobol/ ; entrée = code source (brownfield) ; mode express car entrée riche.
- (note) Sources lues : cobol/Gnu/Inventaire.cbl, cobol/Gnu/Add.cbl, cobol/mf/src/Inventaire.cbl, cobol/mf/test/TestInventaire.cbl, scripts cobol/Gnu/*.sh. Adaptation FR du kata Gilded Rose (E. Bache, MIT 2015).
- (decision) Version de référence des règles = cobol/Gnu/Inventaire.cbl (zones signées, seule version où les règles après échéance s'exécutent) ; écarts Micro Focus consignés dans brownfield.md.
- (capability) CAP-1 Vieillissement quotidien : chaque exécution traite tous les articles de in-items, écrit un article par article lu dans items, même ordre (Inventaire.cbl l.27-79).
- (capability) CAP-2 Article standard (tout nom hors des 3 libellés) : qualité -1/jour si qualité > 0, sell-in -1/jour ; aucune dégradation supplémentaire après échéance (l.31-36, 57-64).
- (capability) CAP-3 Vin rouge : qualité +1/jour, +2/jour quand sell-in < 0 après décrément ; chaque incrément seulement si qualité < 50 (l.37-39, 68-71).
- (capability) CAP-4 Billet de festival : +1/jour, +1 de plus si sell-in avant décrément < 11, +1 de plus si < 6, chaque incrément plafonné à 50 ; qualité = 0 quand sell-in < 0 après décrément (l.40-51, 65-67).
- (capability) CAP-5 Lingot d'or : sell-in et qualité inchangés ; sauf qualité -1 si sell-in déjà < 0 en entrée et qualité > 0 (l.33, 54, 61).
- (capability) CAP-6 Saisie d'article (Add.cbl) : demande nom, sell-in, qualité et ajoute l'enregistrement en fin de in-items, sans aucune validation.
- (constraint) Catégorie déduite par comparaison exacte du nom (casse et espaces compris) avec 'Vin rouge', 'Billet de festival', 'Lingot d'or' ; tout autre nom = standard.
- (constraint) Ordre par article : ajustement qualité du jour -> décrément sell-in -> ajustement après échéance si sell-in < 0 -> écriture. Seuils billet évalués avant décrément.
- (constraint) Bornes appliquées seulement dans le sens de l'évolution : plancher 0 sur les baisses, plafond 50 sur les hausses ; une qualité saisie > 50 n'est pas ramenée à 50.
- (constraint) Enregistrement GnuCOBOL 54 octets : sell-in s9(2), quality s9(2), name x(50) ; fichiers séquentiels in-items (entrée) et items (sortie, recréé à chaque exécution).
- (constraint) Aucune gestion d'erreur : ni file status, ni code retour, ni on size error ; in-items absent = arrêt runtime (add.sh fait touch in-items).
- (decision) Non-goal : la spec décrit le comportement existant, elle ne corrige pas les anomalies ; corrections = décision métier (questions ouvertes).
- (assumption) Condition 'if name is equal to Lingot d'or' en phase après échéance (Gnu l.61, MF l.57) jugée inversion involontaire par rapport au kata (not equal), mais documentée telle quelle.
- (assumption) Valeurs des exemples déduites par lecture du code ; aucun compilateur COBOL disponible pour exécution.
- (question) Un article standard doit-il perdre 2 points/jour après échéance comme dans le kata ?
- (question) Le Lingot d'or doit-il rester immuable même avec sell-in négatif en entrée ?
- (question) Quelle version (GnuCOBOL 54 octets signé ou Micro Focus 58 octets non signé) fait référence ?
- (question) Add doit-il valider qualité 0-50 (Lingot d'or à 80 dans le kata) et le nom ?
- (note) Écarts MF : pic 9(4) non signé -> sell-in jamais négatif, règles après échéance jamais déclenchées ; in-items non fermé ; TestInventaire attend 'fixme', échoue toujours.
