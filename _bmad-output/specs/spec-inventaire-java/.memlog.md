- (direction) Eric demande, avec la méthode BMAD, une spec en français des règles métier implémentées par java/ ; entrée = code source (brownfield) ; mode express.
- (note) Sources : java/src/main/java/com/inventaire/Inventaire.java, Item.java, src/test/.../InventaireTest.java, TexttestFixture.java, pom.xml (Java 1.8, JUnit 5.8.2). Kata Gilded Rose FR (E. Bache, MIT 2015).
- (event) Exemples vérifiés par exécution : compilation de Inventaire.java + Item.java et sonde de 21 cas (javac/java locaux).
- (capability) CAP-1 updateQuality() fait vieillir d'un jour chaque article du tableau, en place, dans l'ordre (Inventaire.java l.15-66).
- (capability) CAP-2 Article standard : qualité -1/jour avant échéance, -2/jour après (sellIn < 0 après décrément), plancher 0 ; sellIn -1/jour (l.17-23, 48-55). Vérifié 0/20 -> -1/18.
- (capability) CAP-3 Vin rouge : +1/jour, +2/jour après échéance, chaque incrément si quality < 50 (l.24-26, 59-62).
- (capability) CAP-4 Billet de festival : +1, +1 si sellIn < 11, +1 si sellIn < 6 (avant décrément), plafond 50 par incrément ; quality = 0 après échéance (l.28-40, 56-58).
- (capability) CAP-5 Lingot d'or : sellIn et quality jamais modifiés, quelle que soit l'entrée (l.20, 44, 52). Vérifié -1/80 -> -1/80.
- (capability) CAP-6 TexttestFixture : affiche l'état de 9 articles jour par jour (défaut 2 jours, sinon args[0]+1) pour test d'approbation texte.
- (constraint) Catégorie = String.equals exact sur name ; tout autre nom, y compris préfixe 'Article fragile', est standard.
- (constraint) Ordre : ajustement du jour -> décrément sellIn -> ajustement après échéance -> article suivant ; mutation en place des objets Item.
- (constraint) Bornes seulement dans le sens de l'évolution : plancher 0 sur baisses, plafond 50 sur hausses ; quality > 50 en entrée conservée (Vin rouge 5/60 -> 4/60).
- (constraint) Aucune validation : Item a des champs publics mutables ; name null -> NullPointerException ; pas de contrôle des bornes à la construction.
- (decision) Non-goals : pas de correction ni d'implémentation de 'Article fragile' ; la spec fige le comportement existant.
- (assumption) 'Article fragile' = équivalent des 'Conjured' du kata (devrait se dégrader 2x plus vite) d'après le commentaire TexttestFixture l.21 ; non implémenté.
- (question) 'Article fragile' doit-il perdre 2x plus vite (-2 avant, -4 après échéance) et comment est-il reconnu (préfixe du nom ?) ?
- (question) La qualité doit-elle être bornée à 0-50 à la création d'un article (sauf Lingot d'or à 80) ?
- (question) Faut-il aligner COBOL sur Java : en COBOL l'article standard ne perd pas 2 points après échéance et le Lingot peut perdre 1 point ?
- (note) Écart COBOL/Java : Inventaire.java l.52 '!equals(Lingot d'or)' vs cobol/Gnu/Inventaire.cbl l.61 'is equal to'. Voir spec-inventaire-cobol.
